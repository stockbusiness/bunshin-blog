### Q-001 アフィリエイトリンクのリダイレクト方式

- 発生タスク：D-8（TASKS.md）
- 状況：自前リダイレクタを後から導入すると、公開済み記事のリンクを全て貼り替えることになる（SPEC 20.1）

  **前提として押さえておくべき事実が2つある。**

  1. **`prisma/schema.prisma` は既に自前リダイレクタを前提にしている。** `affiliate_links` に `code` と `destination_url` があり、`link_clicks` が生イベントを持つ。TASKS D-8 の主な変更先も `src/app/go/`
  2. **ブログはモニター自身のドメインで動く**（SPEC 1.2）。リダイレクタは我々のアプリのドメインに置かれる。つまり `monitor-blog.example.com` の記事から `app.example/go/<code>` へ**別ドメインを経由**することになる

  ここから、技術的な難しさではなく**ASPの規約と成果計測の扱い**が判断の中心になる。

- 選択肢：

  | | 方式 | クリック計測 | 主なリスク |
  |---|---|---|---|
  | (a) | **自前リダイレクタ**（我々のドメイン。スキーマの想定どおり） | 正確 | ASP規約・リファラー・可用性 |
  | (b) | **各ブログのドメイン上でリダイレクト**（WordPress側に仕組みを置く） | 正確 | 30サイトへの導入と維持。プラグインの開発が必要 |
  | (c) | **直リンクのみ。クリックは計測しない** | 無し | `affiliate_links` `link_clicks` が未使用になる |
  | (d) | **直リンク＋ブログ側でクリックイベントを送る** | 概算 | 広告ブロッカーで漏れる |

- 影響範囲：D-8、E-10（記事本文へのリンク埋め込み）、G-4（AI検索流入の判別）、`affiliate_links`・`link_clicks`、**公開済み記事の全て**
- 状態：**解決（2026-08-07）→ 再決定（2026-08-11）。リダイレクタを各ブログの
  ドメイン配下へ移す。** 案件ごとの切り替え（2026-08-07 の決定）はそのまま残す。
  詳細は本文書末尾「Q-001 の再決定（2026-08-11）」

#### (a) を選ぶ前に確認が必要だったこと

**この判断は、こちらで調べられない事実に依存していた。** 確認をお願いした点は次のとおり。

1. **利用予定のASPが、別ドメインのリダイレクタ経由の掲載を許しているか。** 「登録したサイトに直接リンクを設置すること」を条件にしているASPは珍しくない。違反すると**成果が無効になる**
2. **リファラーが我々のドメインになっても成果が計上されるか。** ASPによっては送客元の判定に使う
3. アプリが停止したときに**30ブログ全ての収益リンクが死ぬ**ことを許容するか

**1つ目が「許していない」なら (a) は選べない。** 実験の目的は「AIが運営するブログが稼げるか」を測ること（SPEC 1.2）であり、**成果が無効になると実験そのものが成立しない**。クリックデータの価値より優先される。

#### 決定内容（2026-08-07）

**回答は「ASPによって異なる。許可しているところもあれば、していないところもある」だった。** この前提では、方式を1つに決めること自体が誤りになる。以下を採用する。

##### 1. 案件ごとに方式を切り替える

`affiliate_offers` に**リンクの出し方**を持たせ、記事本文へ埋めるURLをその値で決める。

| 値 | 本文に埋めるURL | クリック計測 |
|---|---|---|
| `REDIRECT` | `/go/<code>` | 正確（`link_clicks`） |
| `DIRECT` | `affiliate_url` をそのまま | サブID・ビーコン（下記） |

**既定は `DIRECT`（安全側）とし、規約を確認できたASPだけ `REDIRECT` に上げる。** 判断がつかないものを許可側へ倒すと、成果が無効になったときに取り返しがつかない。

**モニターに規約の判断をさせない。** ASP単位の既定値を ADMIN が設定し、案件単位で上書きできるようにする。モニターは技術者でも法務でもない。

##### 2. これなら「後から貼り替え」が起きない

SPEC 20.1 が Q-001 を Phase A 着手前としたのは、**リダイレクタを後から入れると公開済み記事のリンクを全て貼り替えることになる**ためだった。

**切り替えの仕組みを最初から入れておけば、この手戻りは起きない。** 記事生成（E-10）が呼ぶリンク組み立てを `src/modules/affiliate/` の1関数に集約し、`REDIRECT` / `DIRECT` の判断をそこだけに閉じる。後から ASP の規約が変わっても、**変わるのは以後に生成される記事だけ**で、既存記事はそのまま動く。

##### 3. `DIRECT` の案件でも計測を諦めない

**(1) サブID（最優先。全案件で入れる）**

ほとんどのASPは、アフィリエイトURLに識別子を付けられる（サブID・sub affiliate id など、名称はASPによる）。

```
https://asp.example/click?a=xxxx&sub=<slot>-<contentItemId>
```

- **ASPが用意した機能なので規約上の問題が無い**
- **成果（＝収益）を記事単位で分解できる。** Phase 0 の目的は「AIが運営するブログが稼げるか」（SPEC 1.2）であり、**クリック数より成果の紐付けのほうが価値が高い**
- 数値はASPの管理画面から取る。Phase 0 は手入力が許可されている（SPEC 11.5）

**`REDIRECT` の案件にもサブIDは付ける。** リダイレクタはクリックを数え、サブIDは成果を紐づける。役割が違う。

**(2) 発リンクのクリックイベント**

`DIRECT` の案件でクリック数も欲しい場合、リンクは直リンクのまま、クリック時にブログ側から計測用のリクエストを送る。**HTML上のリンクは直リンクなので「リンクの設置」は規約に触れにくい。** 広告ブロッカーで漏れるため概算。

**(3) GA4 の外部リンククリック**

SPEC 11.4 が GA4 に言及している。導入済みなら追加コストが小さい。

##### 4. 混ぜて集計しない

`REDIRECT` と `DIRECT` ではクリック数の意味も精度も違う。**`metrics_daily` に出所の分からないクリック数が混ざると、集計が読めなくなる。** 計測方式を区別できるようにするか、少なくとも案件ごとの方式が後から辿れるようにする。

##### 5. 必要になる作業

| 内容 | 位置づけ |
|---|---|
| `affiliate_offers` にリンク方式の列を追加 | **スキーマ変更（単独タスク・DATA_MODEL 9章）** |
| ASP単位の既定値をADMINが設定する仕組み | Phase 0 は設定ファイルまたはSQLで足りる（SPEC 10.3 と同じ扱い） |
| リンク組み立ての集約 | D-1 または D-8 |
| サブIDの付与 | D-1（案件登録時にURLの組み立て規則を決める） |

D-8 の完了条件「記事内リンクが**自前URL経由**になり、クリックが記録される」は、この決定に合わせて**「リンク方式に従って組み立てられ、`REDIRECT` の案件でクリックが記録される」**へ改めた。

**タスクは D-9（スキーマ変更）を追加し、D-1 の依存に加えた。** 案件登録時にリンクの組み立て規則が決まるため、D-1 の前に列が要る。タスク総数 59 → 60。

#### 補足

- SPEC 11.5 は **Phase 0 の収益を手入力で許可**している。つまり (c)(d) でも収益の記録は成立する。失われるのは「クリック数」であり「収益」ではない
- `affiliate_links` と `link_clicks` は **`REDIRECT` の案件でのみ使う**。`DIRECT` の案件では行が作られない。DATA_MODEL 6章の「方式が確定するまでこの2テーブルは確定版ではない」という但し書きは、この決定をもって外せる
- **SPEC 20.1 は本来「Phase A着手前」に決めるとしていた項目**である。Phase A・B を終えてからの決定になったが、**切り替えの仕組みを D-1 の前に入れるため手戻りは生じない**

### Q-005 Search Console の日次データをJSTの暦日へどう対応づけるか

- 発生タスク：A-7（判断が必要になるのは G-2）
- 状況：`DATA_MODEL.md` 10章に「Search Console は日付がUTC基準で返るため、JSTの日付へ変換してから `metrics_daily` に保存する」とある。しかし Search Console が返すのは**時刻を持たない日付文字列**であり、日単位で集計済みの値である

  UTCの1日 `[00:00Z, 24:00Z)` は JST の `[09:00, 翌09:00)` にあたる。**1つのUTC暦日は2つのJST暦日にまたがる**ため、時間単位の内訳が無い以上、JSTの暦日へ割り直すことは原理的にできない。「変換」は実際には**どの暦日に載せるかの取り決め**になる
- 選択肢：
  - (a) UTCの暦日をそのままJSTの暦日として保存する（9時間のずれを許容する）
  - (b) 1日ずらして保存する
  - (c) `metrics_daily` にデータ源のタイムゾーンを持たせ、Search Console 由来の行は「UTC基準の日」として区別する
- 影響範囲：G-2（取得ジョブ）、G-6（`metrics_daily` 集計）、G-7（管理ダッシュボード）。手動収益入力（G-5）はJST基準のため、混在すると同じ `metric_date` の行で基準が食い違う
- 状態：**解決（2026-08-08）。(a) を採用。返ってきた日付をそのまま `metric_date` に入れる**

決定内容：

- **Search Console が返した日付を変換せず `metric_date` に入れる。** 日付をずらさない
- **`metrics_daily` にタイムゾーンの列を足さない**（(c) は採らない）
- **`metric_date` の意味を DATA_MODEL 10章に明記する。** 「Search Console 由来の列はSearch Consoleの暦日であり、JST基準の収益（G-5）と同じ日付で突き合わせると最大1日ずれる」
- G-7 の画面で両者を並べる場合は、この注記を画面にも出す

理由：

- **原理的に割り直せない。** Search Console が返すのは時刻を持たない日付文字列で、日単位に集計済み。時間単位の内訳が無い以上、JSTの暦日へ再配分することはできない。どの方式も「取り決め」にすぎない
- **ずれは全ブログに等しくかかる。** Phase 0 の目的は3ブログ×10名の比較（SPEC 1.2）であり、**系統的なずれは比較を歪めない**。8週間のトレンドを見るのに1日の位相差は影響しない
- (b) の「1日ずらす」は、ずれを別のずれに置き換えるだけで根拠が無い
- (c) の「タイムゾーン列を持つ」はマイグレーションと分岐が増えるわりに、上記のとおり分析上の利得が無い

**残っている確認事項：**

`DATA_MODEL.md` 10章は「Search Console は日付がUTC基準で返る」としているが、**この前提は検証していない**（Google の集計は太平洋時間だという説明も見られる）。**G-1 で実際に接続したときに確かめ、違っていれば記述を直す。** 決定の中身（そのまま入れる）は前提がどちらでも変わらない。

- A-7 が提供した `toJstDate(instant)` は**瞬間**の変換であり、この決定とは別物。日付文字列の割り直しには使わない

### Q-007 ブログのWordPress接続先を途中で別サイトに変更できるか

- 発生タスク：C-1（判断が必要になるのは C-1・C-5）
- 状況：`wordpress_connections.blog_id` は `unique` で「1ブログ＝1接続」だが、**`site_url` を後から書き換えられるか**が `SPEC.md` にも `DATA_MODEL.md` にも定義されていない。SPEC 13.3 には `connect` と `disconnect` の両方があり、切断後に別サイトへ繋ぎ直す経路が読める
- 影響範囲：C-1（接続情報の保存）、C-5（WP同期）、G-2・G-6（計測）、実験データの解釈
- 状態：**解決（2026-08-07）。別サイトへの変更は許可しない**

決定内容：

- **接続後に `site_url` を別のサイトへ変更できない。** 変更しようとした場合は拒否する
- **同一 `site_url` のままの再接続は許可する。** アプリケーションパスワードの入れ替え・権限の付け直し・接続エラーからの復旧はこれにあたり、運用上必ず発生する
- `disconnect` で `connection_status` を `REVOKED` にしても **`site_url` は保持する。** 再接続時は保持している値との一致を確認し、異なれば拒否する
- **モニター自身は変更できない。ただし ADMIN は設定ミスの救済として変更できる**（Q-008 で追記）
- ADMIN の介入でも直せない場合は、そのブログを `CLOSED` にして別のブログとして作り直す

理由：

- 接続先が変わると、そのブログに紐づく `wordpress_posts`・`metrics_daily`・Search Console のデータが別サイトのものと混ざり、**実験データとして読めなくなる**
- Phase 0 の目的は3ブログ×10名の比較（SPEC 1.2）であり、途中で土台が変わった行は分析に使えない
- 一方で認証情報の入れ替えを塞ぐと、パスワード漏洩時や権限変更時に復旧できなくなる。**「サイトの変更」と「認証情報の更新」を分けて扱う**


### Q-008 `CLOSED` にしたブログのスロットを再利用できるか

- 発生タスク：B-4
- 状況：SPEC 2.5 は「1ユーザー当たりブログ：最大3件」、SPEC 13.2 は「削除は物理削除せず `CLOSED`」と定めるが、**`CLOSED` にしたスロットを再利用できるかが書かれていない**

  技術的な制約として `UNIQUE(user_id, slot_number)` があり、`slot_number` は NOT NULL で 1〜3 に限られる。`CLOSED` の行もスロットを保持し続けるため、**再利用を許すには部分一意索引（`CLOSED` を除く）への差し替えが必要**になる
- 選択肢：
  - (a) **再利用しない。** スキーマ変更が不要。`(user_id, slot_number)` が期間を通じて安定した識別子になる
  - (b) 再利用する。マイグレーションが必要。集計時に必ず期間で切り分けることになる
- 影響範囲：B-4、B-5、H-2（オンボーディング）、`metrics_daily` の分析
- 状態：**解決（2026-08-07）。(a) を採用。ただし設定ミスは ADMIN の介入で救済する**

決定内容：

- **モニターは `CLOSED` にしたスロットを再利用できない。** 3スロットは期間を通じて固定
- スキーマは変更しない。`UNIQUE(user_id, slot_number)` をそのまま使う
- **設定ミスは「作り直し」ではなく「ADMIN による修正」で救済する**（下記）

### ADMIN による設定ミスの救済（Q-007・Q-008 共通）

Q-007 で WordPress 接続先の変更を禁止し、Q-008 でスロットの再利用を禁止した。この2つが重なると、**オンボーディングでの接続ミスが 1/3 の枠を恒久的に潰す**。モニターは技術者ではなく、H-2 のオンボーディングは10ステップあるため、ミスは起きる前提で考える。

そのため **ADMIN の手動介入を正規の救済手段とする**（SPEC 3.1「手動介入」）。

- **ADMIN は設定ミスのブログについて、`wordpress_connections.site_url` を変更できる**
- **ADMIN はスロットを解放できる。** 手段はそのブログの物理削除。`Blog → 配下全て` が `Cascade` のため関連行も消える
- **いずれも「そのブログでまだ記事を投稿していない」場合に限る**（`wordpress_posts` が0件）。投稿済みのブログを消すと実測データが失われ、Phase 0 の目的（SPEC 1.2）に反する
- **介入は `audit_logs` に残す**
- **Phase 0 では専用の管理UIとAPIを作らない。** SQL または管理画面の既存機能で行う（SPEC 10.3 の `experiment_groups` と同じ扱い）
- 手順は H-6（操作マニュアル）に記載する

「何回介入が必要になったか」は、オンボーディング設計の評価データとしても使う。

### Q-012 管理者のログイン手段に Supabase Auth を採用するか

- 発生タスク：B-6

  > 推奨：Supabase Auth／メール＋ワンタイムリンク／ADMINロールによる制御

- 状態：**解決（2026-08-07）。(c) を採用。メール＋ワンタイムリンクを自前で実装する**

決定内容：

- **管理者は「メールアドレス＋ワンタイムリンク」でログインする**（SPEC 3.2 の2つ目）
- **Supabase は導入しない。** DBは素の PostgreSQL のまま
- **モニター側は変更しない。** LINE Login（B-1）＋署名付きCookie（B-2）のまま。認証の入口が2つになるが、対象者も画面も分かれている（`/liff` と `/admin`）
- 認証が成功したあとは**既存のセッションCookieを発行する**（B-2 の仕組みを共用）。`requireAdmin` は変更不要
- 照合は `users.email`。**`users.role = 'ADMIN'` の行にのみリンクを送る。** MONITOR のメールアドレスにリンクを送らない

必要になる作業（B-6 の完了条件の外なので別タスクにする）：

| タスク | 内容 |
|---|---|
| **B-10** | ワンタイムトークンのテーブル追加とマイグレーション（DATA_MODEL 9章によりスキーマ変更は単独タスク） |
| **B-11** | ログイン画面・リンク発行・検証・セッション発行 |

### Q-013 メール送信基盤をどれにするか

- 発生タスク：B-11（Q-012 の決定に伴い発生）
- 状況：Q-012 で管理者のログインを「メール＋ワンタイムリンク」と決めたが、**メールを送る手段がまだ無い**。`SPEC.md` にも `TASKS.md` にも送信基盤の記載がなく、環境変数も定義されていない

  Phase 0 の送信量は少ない。管理者1〜2名のログインリンクのみで、モニターへの連絡は LINE（F-2）である
- 選択肢：
  - (a) **Resend。** APIが単純で、ドメイン認証だけで送れる。無料枠が小さめだが Phase 0 の量なら収まる
  - (b) AWS SES。単価は最安。ただしドメイン検証に加え、**サンドボックス解除の申請**が要る
  - (c) SMTP（Gmail・さくら等の既存アカウント）。新しい契約が不要。送信の到達率と資格情報の管理が課題
- 影響範囲：B-11、H-3（エラー通知）が将来メールを使う場合、環境変数、運用コスト
- 状態：**解決（2026-08-07）。(a) Resend を採用**

決定内容：

- **Resend を使う。** HTTP API を `fetch` で叩く。SDKは入れない（依存を1つ増やす価値が無い）
- 環境変数は `RESEND_API_KEY` `MAIL_FROM` `APP_BASE_URL` の3つ
- **3つとも `src/lib/env.ts` では必須にしない。** 未設定でも LIFF 側（モニターの利用）は動く必要があるため、起動を止めない。管理者ログインを試みたときに設定不足として扱う
- **`APP_BASE_URL` は必ず環境変数から取る。** リクエストの `Host` ヘッダーから組み立てると、偽の `Host` を送られたときにリンクの向き先を攻撃者のドメインへ差し替えられる
- **送信先はログインリンクのみ。** モニターへの通知は LINE（SPEC 2.x・F-2）であり、メールへ広げない
- 送信処理は差し替え可能なインターフェースにする。テストは偽の実装で行い、実際の送信は行わない

理由：Phase 0 で必要なのは「管理者1〜2名へリンクを送る」だけで、(b) の申請と (c) の到達率の面倒を負う理由が無い。送信量が増える段階で見直す。

### Q-014 サブIDをアフィリエイトURLへどう付けるか

- 発生タスク：D-9（判断が必要になるのは D-1）
- 状況：Q-001 の決定で「**サブIDは全案件に付ける**」と定めた。ASPが用意した機能なので規約上の問題が無く、`DIRECT` の案件でも**成果を記事単位で紐づけられる**。Phase 0 の目的は収益の実測（SPEC 1.2）であり、クリック数より価値が高い

  ところが**付け方はASPごとに違う**。

  | 形 | 例 |
  |---|---|
  | クエリパラメータ | `...&sub=<値>` `...&s1=<値>` `...&argument=<値>` |
  | パスの一部 | `.../click/<値>` |
  | 付けられない | サブID機能そのものが無い |

  パラメータ名も、使える文字種も、長さの上限もASPが決める。**こちらでは調べられない。** 利用するASPが確定して初めて決まる
- 選択肢：
  - (a) **`affiliate_offers` にパラメータ名の列を持つ**（例：`sub_id_param text nullable`）。`NULL` なら付けない。ASPごとの違いをデータで吸収できる
  - (b) ASP名から実装側のテーブルで引く。列は増えないが、ASPが増えるたびにコード変更が要る
  - (c) 案件登録時に完成形のURLテンプレートを入れてもらう。最も柔軟だが、登録が難しくなる
- 影響範囲：D-1（案件登録時にURLの組み立て規則が決まる）、D-8、G-6（収益の記事別集計）
- 状態：**解決（2026-08-08）。(a) を採用。`affiliate_offers` にパラメータ名の列を持つ**

決定内容：

- **`affiliate_offers.sub_id_param`（text・NULL可）を追加する。** クエリパラメータの名前を入れる（`sub` `s1` `argument` など）
- **`NULL` ならサブIDを付けない。** 案件は普通に登録でき、リンクは `affiliate_url` のまま
- 値は `<slot>-<contentItemId>`（Q-001 の決定どおり）
- **設定するのは ADMIN。** Phase 0 は SQL で入れる（SPEC 10.3 の `experiment_groups` と同じ扱い）。モニターに触らせない
- **`REDIRECT` の案件にも付ける。** リダイレクタはクリックを数え、サブIDは成果を紐づける。役割が違う（Q-001）

**この決定で D-1 のブロックが外れる。** ASPの情報がゼロでも案件は登録でき、サブIDが付かないだけになる。分かったASPから順に `sub_id_param` を埋めれば有効になる。**「着手を止める問題」から「あとから入れる運用データ」へ変わった。**

理由：

- (b)（ASP名から実装側のテーブルで引く）は、ASPが増えるたびにコード変更とデプロイが要る。Phase 0 の運用に対して重い
- (c)（完成形のURLテンプレートを登録してもらう）は柔軟だが、案件登録が難しくなる。登録するのは運営だが、10名×複数案件を手で入れる作業で誤りが増える

| 環境変数のまま | 理由 |
|---|---|
| `DATABASE_URL` | これが無いと設定そのものを読めない |
| `ENCRYPTION_KEY` | 保存された秘密を復号する鍵。DBに置いたら暗号化の意味が無い |
| `SESSION_SECRET` | 管理画面へ入るための認証に要る |
| ~~`LINE_LOGIN_CHANNEL_ID`~~ | **2026-08-14 に画面へ移した**（Q-046）。**この行の判断が誤りだった** |
| `APP_BASE_URL` | 管理者ログインのリンクを組み立てる。**画面へ入る前**に要る |
| `CRON_SECRET` | cron の呼び出し検証。アプリの外から使う |
| `NEXT_PUBLIC_*` | ブラウザ向けは**ビルド時に埋め込まれる**。DBに置いても効かない |

画面から設定できるのは、**アプリが動いた後で初めて要るもの**に限る。

| 画面から設定 | 秘密 |
|---|---|
| `AI_PROVIDER` `AI_MODEL_*` `AI_PRICE_*` `AI_BUDGET_*` | いいえ |
| `ANTHROPIC_API_KEY` | **はい** |
| `RESEND_API_KEY` | **はい** |
| `MAIL_FROM` | いいえ |
| LINE Messaging API のチャネルアクセストークン・シークレット（F-2） | **はい** |

#### 決めたこと

1. **秘密を復号して返す入口を作らない。** 画面に出すのは**末尾4文字と更新日時**だけ。「表示」ボタンを作らない — 一度入れた鍵を読み返す必要は運用上無く、経路があるだけで漏洩面が増える

3. **接続テストは保存前の値でも試せる。** 誤った鍵を保存してから気づく順序にしない
4. **`audit_logs` へは書かない。** `audit` モジュールは未実装で、他モジュールのテーブルを触れない（MODULE_RULES 1）。代わりに設定行そのものに `updated_by_user_id` と `updated_at` を持つ

### Q-030 Search Console OAuth の管理方式

- 発生タスク：G-1（TASKS.md）
- 状況：**SPEC 20.2 が「該当Phase開始前に決定する項目」の4番目に挙げている

     モニターには「**このアプリは確認されていません**」という警告が出る。

     **警告を出したままオンボーディングさせるかは運営の判断**であり、

  3. **オンボーディングの手順数が変わる。** H-2 は10ステップと決まっている

  | (a) | **モニター自身のGoogleアカウントでOAuth** | LIFFから同意画面へ。ブログごとに `refresh_token` を保存 | スキーマのとおり。**Googleの審査か「未確認」警告のどちらかを飲む**。モニターがGoogleのパスワードを扱う場面が増える |

  H-2 のオンボーディング手順、`prisma/schema.prisma`（(b)・(c) なら
  `search_console_connections` の前提が変わる）、`src/lib/env.ts` または
  `app_settings` の目録

決定内容：

- **サービスアカウント1つで全ブログの Search Console を読む。** OAuth の同意画面を使わない
- **モニターは Search Console の「設定 → ユーザーと権限」で、こちらが渡すアドレスを追加する。** H-2 の1ステップに収める
- **`search_console_connections.refresh_token_encrypted` を落とす**（G-1-schema）。ブログごとの行が持つのは `property_url` と接続状態だけ

理由：

- **(a) は Phase 0 の期間と噛み合わない。** `webmasters.readonly` は Google の機密スコープで、

  **日次の取得ジョブ（G-2）が週明けに落ちてデータに穴が空く**
- 審査を通す道もあるが、プライバシーポリシー・ドメイン所有権確認・デモ動画が要り、
  **着手前に日数がかかる**
- **OAuth のスコープはプロパティ単位で絞れない。** (a) はモニターのGoogleアカウントにある
  **全プロパティ**が読める状態になる。(c) はモニターが実験対象のブログだけを指定できる
- **(b) も7日失効を免れない。** 利用者が運営1人でも公開状態の話は変わらない。
  加えて個人アカウントに紐づくため、担当者の交代や2段階認証の再設定で全ブログの取得が止まる
- **モニターがGoogleのパスワードを扱う場面が無い。** オンボーディングの事故が減る（H-2）
- 実装が小さい。OAuthのコールバック経路もトークン更新も暗号化した `refresh_token` も要らない

**引き受ける不利：**

- **SPEC 11.3 の「ブログ単位でOAuth連携」という文言と食い違う。** `docs/SPEC.md` は唯一の正であり、
  **こちらでは書き換えていない。** 文言を直すかどうかは別途の判断が要る。
  なお「ブログ単位で連携する」という趣旨自体は満たしている
  （`search_console_connections` はブログごとに1行で、プロパティもブログごとに指定する）
- **秘密鍵1つが30ブログ分の入口になる。** `ENCRYPTION_KEY` と同じ扱いで保管する（H-5 の0章）
- **運営が全モニターのプロパティを見られる。** (b) と同じ。データ利用同意文（H-6）に含める

**G-1 の完了条件の読み方：** 「ブログ単位で連携でき、トークンが暗号化される」のうち、
暗号化の対象は**ブログごとのトークンではなくサービスアカウントの秘密鍵**になる。
`docs/TASKS.md` は書き換えていない。

**着手時に実測すること（G-1 で確かめる）：**

1. **URL Inspection API（G-3）が要求する権限の水準。** 「制限付きユーザー」で足りるか、
   「フル」または委任オーナーが要るか。**30ブログに後から権限を上げ直してもらうのは避けたい**ので、
   高いほうが要るなら最初からそれを頼む
2. **Search Console が返す日付の基準**（Q-005 に残した未検証事項）

**この2つは G-1 の実装時点でも未実測である。** 実際のサービスアカウントの鍵と、

G-1 は権限の水準を**保存していない**。`sites.get` が返す `permissionLevel` は

そこで「制限付きでは足りない」と分かった場合、モニターに頼む権限が変わるため、
**H-2 のオンボーディングの文面を書く前に確かめる必要がある。**

### Q-031 `metrics_daily.metric_date` が意図した暦日より1日前で保存される

- 発生タスク：G-3（G-2 の統合テストを書いていて気づいた。**原因は G-5 から入っている**）
- 状況：**実測で確かめた不具合。**

  `metric_date` は `date` 型の列だが、書き込む値を
  `startOfJstDay(...)` で作っている。この関数が返すのは
  **JSTの暦日の 00:00 を表すUTCの瞬間**である。

  ```
  startOfJstDay('2026-08-11')  →  2026-08-10T15:00:00Z
  ```

  これを `date` 型の列へ渡すと、**UTCの日付部分が入る。**
  実際にPostgreSQLへ書いて確かめた結果は次のとおり。

  ```
  送った値      : 2026-08-10T15:00:00.000Z
  PostgreSQL側  : 2026-08-10
  ```

  つまり**JSTの 2026-08-11 の行が `2026-08-10` として保存される。**

  影響する書き手は3つで、**どれも同じ関数を使っている。**

  | タスク | 何の日付のつもりか | 実際に入る値 |
  |---|---|---|
  | G-5（手入力） | その週の**JSTの月曜** | 前日（日曜） |
  | G-2（検索データ） | Search Console が返した暦日（Q-005 の決定「**そのまま入れる**」） | 前日 |
  | G-3（インデックス） | 調べた日（JSTの今日） | 前日 |

  **いま壊れていることは無い。** 書き手も読み手も同じ関数を通るため、
  同じ行に集まること自体は保たれており、統合テストも通っている。

  **困るのは外と突き合わせるとき。** G-7 の管理画面に出す日付、
  Search Console の画面と並べたときの日付、モニターに見せる「◯月◯日の週」が
  **すべて1日ずれる。** Q-005 は「Search Console が返した日付を変換せず
  `metric_date` に入れる」と決めているので、**決定と実装が食い違っている。**

- 選択肢：

  | | 案 | 内容 |
  |---|---|---|
  | (a) | **`date` 列用の変換を用意して3か所を直す** | `Date.UTC(y, m, d)`（UTCの真夜中）を渡す。`startOfJstDay` は `timestamptz` の範囲検索用として残す（`jstDayRange` はこのままで正しい） |
  | (b) | 実験開始後に直す | **既存の行と新しい行で1日ずれる。** 突き合わせが余計に難しくなる |
  | (c) | 直さず、ずれている前提で読む | 画面と文書のすべてに注記が要る。**忘れられる** |

- 影響範囲：`src/lib/datetime.ts`、`src/modules/analytics/weekly-result.ts`（G-5）、
  `search-metrics.ts`（G-2）、`index-status.ts`（G-3）、G-6・G-7
- 状態：**解決（2026-08-11）。(a) を採用し、3か所まとめて直した**

決定内容：

- **`jstDateColumn(date)` を `src/lib/datetime.ts` に追加した。** `Date.UTC(y, m, d)` を返す。
  `date` 型の列にはこれを渡す
- **`startOfJstDay` は残す。** `timestamptz` の範囲検索（`jstDayRange`・`atJstTime`）では
  こちらが正しい。**消すと今度は範囲検索が9時間ずれる**
- 書き手3か所（G-5・G-2・G-3）を `jstDateColumn` に付け替えた
- **PostgreSQL が実際に何を持っているかを試験で固定した**
  （`select metric_date::text`）。JSの `Date` を見るだけでは、
  この不具合はまた通り抜ける

理由：

- **いま直すのが最も安い。** 本番にはまだ1行も入っていない（Phase 0 未開始）。
  実験が始まると**古い行と新しい行で基準が変わり**、どちらの日付なのかを
  行ごとに判断することになる
- G-6（集計）と G-7（画面）はこの列を読む。**ずれたまま集計を積むと直す範囲が広がる**
- Q-005 の決定（「Search Console が返した日付をそのまま入れる」）と
  実装が食い違っていた。**決定のほうが正しい**

**再発を防ぐために：** `jstDateColumn` の doc に、どちらをどこで使うかの表を置いた。
`date` 型の列を新しく足すときは必ずこちらを使う。

### Q-001 の再決定（2026-08-11）：リダイレクタを各ブログのドメイン配下へ

2026-08-07 の決定（自前リダイレクタ・案件ごとに `REDIRECT` / `DIRECT` を切り替える）
のうち、**リダイレクタをどのドメインに置くか**を変更する。

#### 変更点

| | 旧（2026-08-07） | 新（2026-08-11） |
|---|---|---|
| リダイレクトの場所 | **Bunshin の共通ドメイン** `/go/{code}` | **各ブログのドメイン** `https://example.com/go/{code}` |
| 実装 | Next.js のルート（D-8・実装済み） | 各WordPressのスニペット ＋ Bunshin の**受信API** |
| クリックの記録 | リダイレクトの中で直接 `link_clicks` へ | WordPress から送信 → 受信APIが `link_clicks` へ |

**案件ごとの切り替え（`link_mode`）・サブID（`sub_id_param`）・302・
`rel="nofollow sponsored"`・IPを保存しないことは、いずれもそのまま。**

#### 理由

**30ブログが同一の外部ドメインへリンクすると、運営者の同一性を示す痕跡になる。**
計測の一元化より footprint の回避を優先する。

Phase 0 は「1人が3ブログを別名で運営する」形（SPEC 1.2）であり、
**共通ドメインへのリンクは、その3つが同じ運営者であることを外から辿れるようにする。**
30ブログ分が集まれば、なおさら分かりやすくなる。

#### 仕組み

1. Bunshin が `{code}` と遷移先の対応を持つ（`affiliate_links`。変更なし）
2. 各WordPressに軽量なスニペット（mu-plugin）を入れ、`/go/{code}` を処理する
3. WordPress側が記録して Bunshin の受信APIへ送る
   - `code`、アクセス日時、リファラの**ホスト名**、AI検索経由か
4. Bunshin は受信したものを `link_clicks` に保存し、日次で `metrics_daily` へ集計する（G-6）
5. **送信に失敗したらWordPress側で保持し、次回まとめて送る**

#### 引き継ぐ必須要件

- `/go/` を `robots.txt` で `Disallow`
- リンクには `rel="nofollow sponsored"`
- リダイレクトは **302**（301はブラウザが覚えてクリックを数えられない）
- **受信APIはブログ単位のトークンで認証する。他ブログのイベントを投入できないこと**
- **個人情報を保存しない。** IPアドレスは保存せず、User-Agent はハッシュ化する

#### 記事生成への影響

E-10 で本文へ入れるアフィリエイトリンクは、**必ず自ブログの `/go/{code}` 形式**とする。
**ASPから取得した生のアフィリエイトURLを本文に書かない**（`REDIRECT` の案件の場合）。

#### 実装済みのものをどうするか

**D-8 は Bunshin 側のルートとして実装・マージ済み**（`src/app/go/[code]/`）。
この再決定により、**そのルートは受信APIへ置き換わる。** 置き換えは D-8 の
やり直しではなく**別タスク（D-12）**として起票する — 完了したタスクの
完了条件を後から変えると、何が済んでいて何が済んでいないのかが読めなくなる。

**`link_clicks` と `affiliate_links` はそのまま使える。** 変わるのは
「誰がその行を作るか」だけで、テーブルの形も集計（G-4・G-6）も影響を受けない。

### Q-045 アプリの実行先を Vercel から Cloud Run へ移すか

**2026-08-14 訂正：** 当初ここに「**Cloud SQL のパブリックIPは使わない**」と

一時証明書で繋ぐ。**この判断（Cloud Run を選ぶ理由）は変わらない** —

- **保管場所の決定（Q-028）を守ったまま、DBを公開範囲から外せる。**

  ソケットかTCPかを知らない
- **`/api/jobs/run` の認可（E-1）がそのまま使える。** Cloud Scheduler は
  任意のヘッダを付けられる。**fail closed の作りを変えずに済む**
- **関数の実行時間の天井が 300秒から60分になる。** `ARCHITECTURE.md` 7章に
  残っていた「記事生成が上限に収まらない可能性」から、
  **プラットフォーム側の制約が外れる**（下の「残る課題」を参照）
- **アプリとDBが同じプロジェクト・同じリージョンに入る。**

#### 残る課題：消化の締め切りを延ばすかどうか

`DRAIN_BUDGET_MS`（50秒）と `DEFAULT_JOB_TIMEOUT_MS`（45秒）は、
**Vercel の上限ではなく cron の間隔（毎分）に合わせてある。**

延ばすと**消化が重なる。** 取り合いは `SELECT ... FOR UPDATE SKIP LOCKED`
で防げるので同じジョブを二重に実行することは無いが、
**AI呼び出しが同時に何本も走る**ことになる。

**これは費用と流量の判断で、実行先の判断とは別。**
実際に記事生成を回して 45秒で足りるかを見てから決める（E-10）。
**ここでは変えない。**

#### 粒度は2階層にする（2026-08-15）

利用者から「**粒度は細かい方が記事の精度がよくならないか**」という
問いがあり、調べた。**半分は当たっていて、半分は外れていた。**

**記事本文の生成にジャンルは渡っていない。** `ArticleGenerationInput`
（`content-generation/ai.ts`）の中身は contentItem・persona・usableFacts・
offer・internalLinks・existingTitles の6つで、**ジャンルは無い。**
本文の書きぶりを決めるのは分身・案件の `facts`・キーワードと検索意図。

**ただし題材選びには効く。** `genreName` は3か所でAIへ渡る。

| どこ | 何に使うか |
|---|---|
| STEP 2 | 案件の需要判定（`askDemandSafely`） |
| STEP 4 | 検索意図の言語化（`writeSearchIntents`） |
| STEP 4 | キーワード案（`writeKeywords`） |

**「投資」より「つみたてNISA」のほうが、出てくるキーワードは良くなる。**
効くのは**記事の精度ではなく、記事の題材選びの精度**である。

細かくすることの代償は3つ。

1. **`ymylRisk` は行ごと。** 細かくすると個別に `HIGH` を付けることになり、
   **1つ付け忘れるとそこだけ素通りする**
2. **ジャンル別の集計が薄まる。** 30ブログで細かくすると1ジャンル1ブログに
   なり、**ジャンル別の比較ができない。** それは90日検証の目的そのもの
3. **選びにくくなる**（Q-047 と同じ形の詰まり）

**`genres` には既に `category` 列がある。** これを使って2階層に分ける。

| 列 | 粒度 | 使い道 |
|---|---|---|
| `category` | **粗い** | **`ymylRisk` の単位**・ジャンル別の集計 |
| `name` | **細かい** | **AIに渡す言葉**（STEP 2/4） |

**同じ `category` の行は同じ `ymylRisk` にする。** DBは強制しないので、
`createGenre` が足すときに弾く。

#### 種に入れるのは YMYL だけ（2026-08-15）

マイグレーション `20260815000000_seed_ymyl_genres` で、
**SPEC 9.2.2 に列挙された6分野だけ**を `HIGH` で入れた。
**解釈を足していない**（何が YMYL かの線引きは SPEC 18章の
未確定事項 11 で、まだ決まっていない）。

**通すためのジャンルは種に入れない。** 実際に何を書けるかは
**案件と対になって決まる**（案件0件は停止条件）ので、

**実装側からは (b) を薦めた。** 10人・90日の実験に対して (c) は重く、
リッチメニューは全員共通で一度決めたら変わらないため。**利用者の判断で (c)。**

**採る理由はある。** 行き先が `NEXT_PUBLIC_LIFF_ID` を含む LIFF のURLで、
**IDが変わると全部のボタンが黙って壊れる**（本番チャネルへ移すときに必ず起きる）。
手作業だと4つのURLを入れ直しになるが、ここから作れば押し直すだけで済む。

**引き換えに失うもの。APIで作ったリッチメニューは、LINE公式アカウント

**両方から触る運用にはできない。** 承知のうえで、管理画面を唯一の入口にする。

#### 決めたこと

**保存と適用を分ける。** 保存は LINE を触らない。**押すまで誰にも出ない。**
出す前に、絵の上に升目を重ねて画面で確かめられるようにするため。

**途中で失敗したら、いま出ているメニューを壊さない。**
`create` → 画像 → 既定 の順で、失敗したら作りかけを片づけて投げる。
**既定は差し替えない。** 古いものを消すのは既定を差し替えた**後**
（先に消すと、差し替えに失敗したとき誰にもメニューが出なくなる）。

**片づけ残りを黙って隠さない。** 古いメニューを消せなかったときは
`staleRichMenuId` を返し、画面に出して人に片づけさせる。

**LINE に断られる前に断る。** APIのエラーは英語で、何を直せばよいかを
画面に出せない。字数・枠からのはみ出し・重なり・`https` 以外の行き先を
こちらで見る。**画像は申告ではなく中身から読む**（PNG/JPEG の頭）。

**縦横比が枠と違う画像を断る。** LINE は画像を枠へ引き伸ばすので、
比が違うと**管理画面で見た升目と、指で押す場所が食い違う。**

**決まりはDBにも置く。** 字数・画像の大きさと種類・「画像4列はそろって
入るか空か」・「適用の2列はそろって入るか空か」を CHECK で持つ
（`app_settings` と同じで、アプリ側の書き方に依存させない）。

**画像は `rich_menus` に置く。** LINE の上限が1MBなので収まる。
置き場所を増やすより、**下書きと画像が一緒に残る**ほうが
「適用し直す」が確実になる。

**1行しか持たない。** 全モニター共通で、出し分けが Phase 0 に無い。

#### 管理画面（`/admin/rich-menu`）

**絵の上に升目を重ねて見せる。** 座標を数字だけで決めさせない —
4つの数を6組打つのは現実的でなく、**打ち間違いは「押しても何も
起きないボタン」**として本番に出る。**見たまま確かめられる**ようにする。

**升目は型で入れる。** 2段3列・2段2列・1段3列・1段2列と、細い枠の2つ。
数の入力は残すが**ふだんは触らない。** 型を変えても、**入れてある
名前と行き先は消さない。**

**端数は最後の升へ寄せる。** 2500 は 3 で割り切れない。そのまま並べると
**1pxの隙間**ができ、そこだけ押しても反応しない。

**行き先は選ばせる。** `LIFF_BASE_URL` から組み立てた候補から選ぶ。
**手で打たせない。**

**「行き先をいまの設定に合わせる」を置く。** LIFF ID を変えたときに
押すためのもので、**Q-054 で管理画面から作ることにした一番の理由がこれ。**
**知っている画面だけを入れ直す** — 外部のURLは触らない
（勝手に書き換えるほうが危ない）。

**画像と押す場所がそろうまで「LINEへ出す」を押せない。** 画像のない
メニューは LINE が受け取らない。**保存はいつでもできる**（途中でやめられる）。

**公式アカウントマネージャーから編集できなくなることを画面にも書く。**
後から知ると、**直せない状態で気づく**ことになる。
