## 1. 計算できるもの

### 1.1 オンボーディング完了率

```
分子: users.onboarding_status = 'COMPLETED'
分母: users.activated_at IS NOT NULL（参加を認めた人）
```

**分母を「登録した人」にしない。** 招待しただけ・承認待ちの人を入れると、
**こちらが承認していない期間の長さで率が動く。**

`onboarding_status` は `GET /api/onboarding` が導いて書き戻している（H-2a）。
**正は導いた結果で、列はその写し。**

### 1.2 LINE提案反応率

```
分子: approvals で status が APPROVED / SKIPPED / REVISION_REQUESTED
分母: approvals で sent_at IS NOT NULL
```

**分母は「送れた提案」だけ**（J-5）。作ったが送れていないものを入れると、
**通知が止まっているだけの人が「反応が悪い」に見える。**

**`VIEWED` を分子に入れない。** 開いて閉じたのは判断ではない。

`/admin/monitor-activity` が直近14日で同じ計算をしている（J-5）。
**8週間の集計は期間を変えるだけ。**

### 1.3 承認率

```
分子: approvals.status = 'APPROVED'
分母: 1.2 の分子（判断されたもの）
```

**分母を「送れた提案」にしない。** 反応率と承認率が同じものになり、
**「押しているが承認していない」が見えなくなる。**

### 1.4 WordPress投稿成功率

```
分子: jobs で job_type = 'WORDPRESS_POST' かつ status = 'SUCCEEDED'
分母: 同 job_type で status が SUCCEEDED / FAILED
```

**`jobs` の行は消していない**（削除する処理がどこにも無い）。分母が
後から失われる心配は無い。

**再実行（H-14）は元の行を戻すので、行数は増えない。** 最後の結果だけが残る。

### 1.5 1件の確認時間

```
approvals.responded_at - approvals.viewed_at
```

**`sent_at` からではない。** 届いてから開くまでは**モニターの生活の
都合**で、確認にかかった時間ではない。

**`viewed_at` が無い判断は数えない**（LIFF を開かずに操作した記録）。

### 1.6 AI費用

```
ai_usage_logs.cost_usd を user_id・期間で合計
```

**単価が未設定だと `cost_usd` が入らない**（E-3）。検証を始める前に
`AI_PRICE_*` がすべて設定されていることを確かめる（`DEPLOY.md` 3.3）。

## 2. 足りないもの

### 2.1 「8週間継続率」の継続とは何か（Q-043）— **決定済み**

決めた日：2026-08-17（利用者の正式回答）。

> **8週間継続率は、利用開始から43日目〜56日目の14日間に、
> 承認・修正依頼・見送りのいずれかを1件以上行ったモニターを
> 「継続」と定義する。**

```
分母: users.activated_at から56日を経過した全モニター
分子: そのうち、43日目〜56日目に1件以上判断したモニター
```

**窓は動かさない。** 起点は `users.activated_at` で、**利用者ごとに違う固定期間**。
移動する14日窓（`ACTIVITY_WINDOW_DAYS`）にすると、
**集計した日によって率が動く。**

**提案が一度も送られていない人を分母から外さない。**
外すと、**ジョブ停止や通知障害による未活動が見えなくなる。**

そのぶん、原因を分けるために次を別に記録する。

| 見るもの | どこから取るか |
|---|---|
| 対象期間に提案が1件も届かなかった人数 | `approvals.sent_at` |
| 提案を受け取った人の反応率 | `approvals.sent_at` / `responded_at` |
| ジョブ失敗件数 | `jobs.status = 'FAILED'` |
| LINE通知失敗件数 | `PROPOSAL_NOTIFY` の失敗（**送信単位の記録は無い**） |

**J-5 の `judgeApprovalActivity` はそのままでは使えない。**
あちらは**移動する14日窓**で、日々の見守り用。
利用者ごとに窓の位置が違う集計を別に足した（`approvals/retention.ts`）。

**画面は `/admin/monitor-activity`。** 上の表（直近14日）とは
別のまとまりに出している — **同じ表に混ぜると読み違える。**

### 2.2 「見逃した事実誤認」の記録先（Q-044）— **解決済み**

**`fact_issues` を作った**（J-7）。`/admin/fact-issues` で集計を見る。

```
分子: fact_issues で severity='MAJOR' かつ caught_before_publish = true
分母: fact_issues で severity='MAJOR'
```

**公開前に気づいたものも、公開後に見つかったものも同じ表に入れる。**
分けると、分母を組み立てるのに2か所を足し合わせることになり、
**片方を数え忘れたときに率が良く出る。**

**残る仕事は仕組みではなく運用。** **公開後に誤りを見つけたら必ず
入れる**という約束が無ければ、表は空のままになる。**空の表は
「誤りが無かった」ではなく「数えていなかった」**である。

#### 運用の約束（2026-08-17 決定）

> **事実誤認は、運営管理者が毎週1回まとめて登録する。重大な誤りは
> 発見時に即時登録する。モニターはLINEで報告するだけとし、
> 公開済み記事についても毎週一定数を抽出確認する。**

| | |
|---|---|
| 登録する人 | 運営管理者。**モニターに入力させない**（Q-058 の原則） |
| 頻度 | 週1回まとめて。**重大なものは発見時に即時** |
| モニターの報告 | LINEで言うだけ。**専用フォームを作らない** |
| 抜き取り確認 | 毎週、公開済み記事から**10件**（負荷が高くても最低5件） |

抜き取りの優先順位は、収益記事 → 数値・料金・条件を多く含む記事 →
最近更新された案件を扱う記事 → 修正依頼があった記事 → 無作為。

**「確認したが0件だった」を記録できる場所が要る。**
報告された誤りだけを見ると、**空の表が「誤りが無かった」と読める** —
`fact_issues` が解こうとしたのと同じ問題が、確認そのものに起きる。

#### 記録する場所

| | どこ |
|---|---|
| 誤りそのもの | `fact_issues`（発見経路・修正状況・修正完了日時を含む） |
| **確かめたこと** | `fact_review_weeks`。**確認した週にだけ行を作る** |

**`fact_review_weeks` は0件で行を作れない**（DBの CHECK）。
0件の行は「確認していない」と同じ意味になり、**この表を作った理由が消える。**

**画面は `/admin/fact-issues`。** 今週まだ確かめていなければそう出る。
**直っていない誤りの数も別に出す** — 記録しただけで直っていないのが
いちばん悪い。

## 3. 目標に無いが、見ておくべきもの

**成果（コンバージョン）は SPEC 16.2 の目標に入っていない。**
「短期で断定せず3〜6か月追跡する」とされているため。**それでよい。**

ただし**記録は最初から取る**（後から遡れない）。

| 見るもの | どこにあるか |
|---|---|
| クリック | `link_clicks`（D-12） |
| 表示・掲載順位 | `metrics_daily`（G-2） |
| インデックス | `metrics_daily.indexed`（G-3） |
| 記事の厚み | `article_versions.risk_flags`（J-4） |

**J-4 の厚みのフラグは、成果と突き合わせる材料になる。**
「薄い記事は成果が出ない」という当たり前を、**このデータで確かめられる。**
閾値（1200字・見出し3つ）は推定なので、**実測で見直す**（Q-042）。
